# Релей: развёртывание и что изменилось

## Зачем он появился

До этого bookmarklet носил в себе настоящий токен Telegram-бота, а `build_guide.js`
запекал его в `public/index.html` — страницу, которую Vercel отдаёт публично.
То есть **токен был опубликован в интернете**. Кто угодно, открыв страницу установки,
мог его забрать, прочитать через `getUpdates` чаты всех пользователей и слать
сообщения от имени бота.

Плюс каждая вкладка звала `getUpdates` напрямую, без `offset`. Это возвращает апдейты
**всего бота**, поэтому вкладка одного пользователя видела команды и chat id остальных,
а неподтверждённый бэклог рос сутки и перекачивался заново каждые 4 секунды из каждой вкладки.

Теперь токен живёт только в переменных окружения серверных функций. В браузер уезжает
персональный ключ — HMAC от chat id, — который умеет ровно две вещи: отправить сообщение
в этот чат и прочитать команды из этого чата.

## Сначала — отозвать старый токен

Развёртывание нового кода **не отменяет утечку**: токен уже был публичным.

1. Открыть @BotFather → `/revoke` → выбрать бота → получить новый токен.
2. Прописать новый токен в Vercel и в `config.ini`.
3. Все ранее выданные закладки перестанут работать (ключи выводятся из секрета) —
   это ожидаемо и правильно: пользователи перегенерируют ссылку на странице установки.

## Переменные окружения в Vercel

| Переменная | Где нужна | Значение |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | runtime, функции `api/*` | новый токен от @BotFather |
| `RELAY_URL` | build | публичный origin проекта, например `https://visabot-nine.vercel.app` |
| `RELAY_SECRET` | runtime, опционально | если не задан, ключи выводятся из `TELEGRAM_BOT_TOKEN` |

`RELAY_URL` можно не задавать: сборка подставит `VERCEL_PROJECT_PRODUCTION_URL`.
Но на превью-деплоях это будет другой домен, так что для продакшена лучше задать явно.

Важно: `TELEGRAM_BOT_TOKEN` больше **не участвует в сборке**. Если он выставлен,
`build_guide.js` напечатает предупреждение и проигнорирует его. В `public/` секретов нет —
на это есть тест.

## Эндпоинты

- `POST /api/enroll` `{chatId}` → шлёт шестизначный код в этот чат.
- `POST /api/enroll` `{chatId, code}` → проверяет код, возвращает `{key}`.
- `POST /api/notify` `{chatId, key, text, silent?}` → отправляет сообщение.
- `GET /api/commands?chatId=&key=&after=` → команды **только этого чата** плюс `cursor`.

Код подтверждения выводится как HMAC от `(chat id, десятиминутное окно)` — хранилища не нужно,
а серверлес его и не имеет. Владение чатом доказывается тем, что код доставлен именно туда.

## Как теперь ограничен бэклог Telegram

`offset` подтверждает апдейты для всего бота, поэтому подтверждать их сразу нельзя —
затрутся команды других пользователей, которые их ещё не забрали. Вместо этого релей
подтверждает только апдейты **старше 10 минут**: любая живая вкладка опрашивает раз в 6 секунд
и давно их видела. Бэклог ограничен, чужие команды не теряются, внешнее хранилище не нужно.

Ответ `getUpdates` кэшируется на 2 секунды и разделяется между всеми пользователями,
так что N вкладок дают не N запросов к Telegram, а один.

## Выдача ссылки вручную

```bash
python3 generate_bookmarklet.py 715697717
```

Берёт `url` и `secret` из секции `[RELAY]` в `config.ini` (если `secret` пуст —
использует токен бота). Ключ считается тем же HMAC, что и на сервере; на совпадение
двух реализаций есть тест.

## Тесты

```bash
npm test
```

19 тестов: разбор ответов VFS (включая регрессию на «неизвестный формат ≠ слотов нет»),
вывод и проверка ключей, коды подтверждения, совпадение JS- и Python-реализаций,
и защита от повторного попадания токена в браузер.

Питоновская часть — как раньше:

```bash
python3 -m pytest tests/ -q
```
